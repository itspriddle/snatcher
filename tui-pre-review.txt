  2. Three structural gaps

  No multi-select anywhere. This is the biggest omission. The CLI's whole
  mutation model is a selector (ids/hashes/--all), and the TUI can only ever act
  on one torrent or on a whole filter group. Everything in between — "pause
  these five" — is unreachable. Adding marks also fixes the filter-pane blast
  radius problem, because bulk becomes explicit rather than focus-dependent.

  The fix implies one governing rule worth writing into the vision as a
  principle:

  ▎ Every action key operates on the marked set if any marks exist, otherwise on
  ▎ the cursor row.

  That single line makes every action binding self-consistent and maps 1:1 onto
  transmission.Selector.

> yes lets add multi-select and the vision update.

  No defined esc ladder. "Spamming esc gets back to the torrents page" is a
  vibe, not a spec, and esc currently has three different local meanings. It
  needs one ordered stack, e.g.: close overlay/modal → exit search input → clear
  search → clear marks → deselect row → return to torrents window → (root: does
  nothing; never quits).

> we should define it properly. i guess it is a vibe, but that is the behavior
> i want in the end. will definitely need care and thought as we add different
> windows and ui elements.

  tab conflates pane focus with tab selection. "filter → torrents → overview →
  files → trackers → peers → labels → filter" means seven presses to get out of
  the detail pane, and it duplicates [/], which already cycles tabs. Cleaner:
  tab/shift-tab cycles panes only; [/] (and h/l when the detail pane is focused)
  cycles tabs. Given the vision says "like a vim window," ctrl-w h/j/k/l for
  direct pane targeting is the cohesive power-user addition.

  3. Missing bindings

  Nothing is specified for: g/G (top/bottom), ctrl-d/ctrl-u (half page), n/N
  (next/prev search match), home/end/pgup/pgdn. For a vim-flavored audience
  that's a conspicuous hole. Also missing: no way to switch servers in the TUI
  at all, despite named servers + --server being core to the CLI. And no torrent
  move (set location) anywhere — not as a key, not in the action menu — despite
  torrent move/mv shipping. The action menu also omits --sequential-download
  and --group, both of which exist on torrent update.

> yes good call, all of these should be added.

  4. CLI parity is inverted for the detail pane

  The vision's rule is "anything TUI can do can be done with the CLI." The
  detail pane breaks it hardest: files, peers, trackers, and pieces have no CLI
  representation at all — I checked, list.go has a peers count column and that's
  it. The files tab is worse, because it's the only place in the design that
  mutates something the CLI can't touch (priority high/normal/low,
  wanted/unwanted).

  That's not a keybinding problem, but it's the thing most likely to derail the
  TUI build: you'd be adding RPC surface and a domain model under a TUI
  deadline. Suggest landing snatcher torrent files <id> (list) and file
  priority/wanted mutation on the CLI before the files tab, so the TUI is a view
  over an existing capability like every other pane. Same for torrent peers /
  torrent trackers, even if read-only.

  Missing from both sides: file/torrent rename (torrent-rename-path) — worth
  deciding now whether it's in scope.

> good finding. we should add these needed cli's first. prowlarr search still
> needs to be done as well. lets identify them.

  5. Terminal-level gotchas that constrain the keymap

  - ctrl-l (prowlarr: focus search) is the universal redraw/clear convention.
  Users will hit it expecting a repaint. Drop it; / is enough.

> understood and agreed

  - Never bind ctrl-j, ctrl-i, ctrl-m, ctrl-h — legacy terminals send them as
  Enter/Tab/Enter/Backspace. Kitty protocol disambiguates, Bubble Tea v2
  supports it, but you can't rely on it. This kills the otherwise-obvious
  ctrl-j/ctrl-k for queue moves.

> yes good call

  - Avoid ctrl-s/ctrl-q — XOFF/XON flow control on many setups. Relevant if you
  want ctrl-s for "save settings."

> yes good call

  - Alt/Option chords need "use Option as Meta" on macOS Terminal.app. Don't put
  anything essential there.

> yes. i dont want to use alt/option at all. they perform weirdly on Macos
> Terminal.app which I use (i.e. fzf I can't use option chords at all even
> with that option set).

  - Clipboard is write-only. tea.SetClipboard (OSC 52) copies fine, but OSC 52
  read is disabled in nearly every terminal for security. So y-anything works;
  an "add from clipboard" affordance in the upload modal cannot — you must rely
  on the terminal's own paste (enable bracketed paste).

> we can skip any read from clipboard stuff. users can just paste manually like they'd
> do in most other apps

  - Settings window vs huh keymaps will fight. The spec says
  tab/shift-tab/up/down all move between fields, but inside a Select or a
  multi-line input, up/down belong to the widget. Spec it as: tab moves fields,
  up/down belong to the focused field.

> i am fine with whatever approach will let someone navigate through the
> fields properly. in a prior spike of this app i tried doing the navigation
> after we added all the form fields. there wasn't enough thought put into it
> so there were weird little surprises/bugs. the spec notes on it were trying
> to account for that and think about it earlier.

  6. What's already right

  Worth keeping deliberately: [/] cycles tabs in both the detail pane and the
  settings window — that's the one binding that's already cross-window
  consistent. f = "refine what's shown" is consistent across torrents and
  prowlarr. And the settings tabs (Download, Network, Bandwidth, Queue) map
  exactly onto the existing settingCategory constants, so the TUI can drive off
  the same table that powers server show --category. General + Polling are the
  two client-side additions, and those need a new config.json schema section —
  today internal/config only knows servers + default_server.
